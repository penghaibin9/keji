# 首页与统一待办提速记录（2026-10-13）

## 现象

学校服务器上管理员打开“工作总览”“统一待办”要一分钟以上（nginx 504）。只读测量：`/api/portal/workbench` 超过 60 秒，`/api/todos` 约 35.6 秒，`/api/connections/summary` 约 8.2 秒，通知和统计都在 0.1 秒内。

## 原因与改法

1. **审计表没有 `result` 索引。** 安全提示按 `result='DENIED'` 汇总，13.7 万行里只有 746 行是 DENIED，却要扫全表，每条 10 到 30 秒，一个页面跑好几次。
   - 新增迁移 `20261013_0005`：建三个索引。服务器上已手工建过的同列索引会改成契约规定的名字（MySQL 用 RENAME INDEX，其他库先删后建），不会跳过：安装校验按名字比对，名字不对会报 SCHEMA_INDEX_MISMATCH。三个索引都已写进 `backend/audit_index_schema.json`。
     - `audit_events(result, created_at)`（`ix_audit_result_time`）：已有同列索引（任意名字，如 `ix_audit_events_result_created`）就改名为本名。
     - `audit_events(created_at DESC, id ASC)`（`ix_audit_created_desc_id`）和 `inbound_batches(created_at DESC, id ASC)`（`ix_inbound_batches_created_desc_id`）：操作日志和入站批次列表按“最新在前、同时间按 id”排序，两列方向相反，普通索引用不上，每次打开都对整表排序（服务器测得 53.8 秒和 26.3 秒）。按名字判断是否已存在。
   - 入站批次列表只取摘要列，不再读 `receipt` 大字段。
   - 待办和工作总览只需要“要不要提示、为什么”，改用 `security_alert()`，不再查近期对象、关键变更、失败任务清单；完整的 `security_summary()` 仍用于“操作日志与安全审计”页。
2. **按教师逐个查库。** 缺负责人上交（`identities.stage_handler`）原来每位教师查几次数据库，733 位老师约 3500 次查询。现在组织树、负责人、教师所属组织各一次取全，约 40 次查询。
3. **授课认定待办每次全量重算。** 22 万条教师课程表在 Python 里逐条算一遍要十几秒。现在：
   - `reference_data.all_credit_groups` 按“数据指纹”（课程表、认定记录、课程总库、教职工表的行数和版本合计）缓存，数据变了指纹就变；每个进程最长保留 30 分钟；同时来几个请求只算一次。
   - 只读取算分用到的列，教务课程不取 extra，认定记录一次查出。
4. 考核待办在数据库里先排除已归档的考核，不再全部取回再判断。

## 效果（模拟 733 位老师、22 万条课程表、全部缺负责人，SQLite）

- 查询次数：约 3500 → 约 40。
- 首页：没有缓存时约 6.4 秒（修复前）；命中缓存约 0.1 秒。数据变化后的第一次仍要重算约 9 秒（本地模拟，全部课程都关联账号的最坏情况）。

## 没解决或要继续看的

- `/api/connections/summary` 的 8 秒：服务器只读测量显示连续三次 8.26 / 4.55 / 2.19 秒（越调越快），`tasks` 只有 19 行，不是任务表的问题；`inbound_batches` 712 行却有 138MB（每行约 200KB，主要是 `receipt`）。状态页原来整行读出批次，现在 `batch_facts` 只取需要的列和 `receipt` 里的三个值。效果要上线后在服务器上再量。
- `inbound_rows` 已有约 59.5 万行，每周全量同步再加约 25 万行，需要给已确认批次做保留和清理，另行规划。
- 授课认定缓存在多进程下每个进程各算一次；认定一门课后，该进程和另一个进程的下一次打开会重算（约 9 秒的最坏情况）。后续可改成把汇总落表，需要再加迁移。
- 交付清单、接口目录、数据字典是脚本生成的，打包前要在 Windows 上重新生成。

## 附：学校反向代理后的真实来源 IP（可信代理）

学校用域名访问时前面有反向代理（HTTP/1.0），所有用户到我们这里的来源地址都是代理的地址。登录限流按来源地址计数，不处理的话几个人输错密码就会把全校都限流。

- 新增配置 `ND_TRUSTED_PROXIES`（逗号分隔，可写网段），**默认留空即关闭**。在 `deploy/.env` 里加一行，例如 `ND_TRUSTED_PROXIES=10.255.1.34`，重启 api 容器生效。写错会在启动时报“可信代理地址格式不正确”。
- nginx 把收到的 `X-Forwarded-For` 原样放进 `X-Client-Chain` 交给程序（程序原来不读 `X-Forwarded-For`，这一点不变）。
- 程序只在直连方（学校代理）在可信列表里时才采用这条链：从右往左跳过可信代理，第一个不是可信代理的地址就是真实来源；客户端自己写在最左边的内容不会被采用。链为空、格式不对时回到直连地址。
- 前提：学校代理要把真实客户端地址写进 `X-Forwarded-For`。上线前请学校网络确认；没有写的话效果和不配置一样。
- 目前只有登录限流用到来源地址（`routes/auth.py`）。
- 测试：`tests/r2/test_trusted_proxy.py`（默认关闭、可信代理、防伪造、写错配置启动失败、配置前后全校共用一个地址的对比）。
