# 上线前性能审计记录（2026-10-21）

## 测法

本机合成数据：3200 位教师、20 个学院 / 100 个教研室、20.8 万条教师课程表、6.4 万条培训记录、资质和考核各 6400 条、2.6 万条流转记录。
用浏览器按教师、教研室、学院、学校、管理员五个账号逐个点开左侧菜单计时；慢接口用 cProfile 和查询计数定位。
并发测试用 MySQL 8.0、按 `Dockerfile.api` 开 2 个进程。绝对时间只作参考，前后对比有意义。

## 已改

1. `approval_center.pending()` 先批量取齐原单、教师、组织、周期和“进入当前环节时间”，不再每条待办查五六次库。
   首页、待办中心、角色待办数（每 60 秒刷新一次）都走这里。学校身份 1.2 万条待办：约 1.4 万次查询、5 秒 → 0.5 秒；学院 0.26 → 0.05 秒。
   与原逐条查询逐字段比对一致（学校、学院、教研室、管理员 6 个账号），并加了测试。
2. `/organization-workbench` 传 `size` 时只回这么多条待办（总数不变），前端传 6。学校身份原来一次 2.4MB。
3. nginx 加 `gzip_http_version 1.0; gzip_proxied any;`：学校反向代理用 HTTP/1.0 转发时也压缩。本机实测 app.js 509827 → 188546 字节。
4. 登录页背景图按原底色合成后存为 JPG：1.48MB → 0.10MB。原 PNG 未删。

## 没改、建议跟进

- 授课认定“待认定”筛选每次重算全校课程（本机 13 秒）。可按 `all_credit_groups` 的数据指纹另做一份含未关联账号课程的缓存。
- `--workers 2`：本机 4 核，100 位教师同时打开首页 19 秒，改 4 个进程后 7 秒。按学校服务器核数调整；授课认定缓存是每个进程各一份。
- 学校、学院身份每次刷新都取全校教师名单（3200 人 16 个请求约 1.1MB），并在筛选栏放 3200 个候选项。可改成按需搜索。
- 数据核对页每条异议单独请求原业务摘要。
- `frontend/assets` 里 training-course.png、training-base.png、training-tea.png、campus-linework.png 没有页面引用，共约 8.6MB。
