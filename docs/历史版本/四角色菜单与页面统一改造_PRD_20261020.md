## 1. 需求背景与已确认方向

用户反馈：普通教师、教研室、学院、学校看到的菜单不同，同样菜单进入后的页面也不同，切换身份后需要重新寻找功能，难以判断数据和操作是否正确。

本次改造应整理现有系统，不另建四套页面，不增加新的菜单配置平台，不借机扩展业务范围。

### 1.1 用户已经确认的要求

1. 四种角色使用统一的菜单结构；共同业务同名、同序、基本布局一致，无权入口隐藏。
2. 切换身份后尽量停留在同一业务，新身份无权访问时才回到工作总览。
3. 教师进入项目、课程、基地、师资业务时先看到相应记录，再发起申报或查看进度。
4. 学校文件规定的名称、业务内容、职责与制式表格必须保留，不由设计人员随意替换。
5. 优先保留现有已正常工作的查询、详情、表单、附件、审批和历史记录。
6. 先根据真实页面与代码审计，再确定保留与修改范围。

## 6. 菜单与入口设计

### 6.1 一致性要求

**需求01 公共界面稳定**

- 公共抬头、侧栏宽度、搜索、身份入口、退出入口和选中样式跨业务保持一致。
- 业务专用样式只作用于业务内容区域，不覆盖公共导航。
- 复用现有普通业务页公共外观；不新增配色、主题或布局切换器。
- 驾驶舱可保留专用展示布局，但必须保留清楚的返回工作台入口。

**需求02 入口与授权一致**

- 菜单、菜单搜索、首页快捷入口、通知跳转及页面访问采用相同的前端资格判断。
- 资格包括现有权限、当前身份、组织范围、系统管理员条件及专项职责；不能只按角色层级判断。
- 后端继续独立校验。隐藏按钮不代替服务端授权。
- 整页无可访问内容时隐藏菜单；复合页面仅展示有权使用的页签。
- 有申报权限、无业务库查看权限时，允许进入本人申报区，不调用无权业务库接口。
- 权限不足不使用“重新读取”作为唯一恢复方式；提供返回有权入口并解释原因。

### 6.2 第二批目标导航建议

以下为待整体评审的设计建议，非学校规定的原始菜单树。文件明确命名的功能保持原名或作为明确可见的子功能；首页允许按职责展示不同重点。

| 分组建议 | 菜单固定顺序 | 说明 |
| --- | --- | --- |
| 工作台 | 工作总览、审批中心、政策通知 | 工作总览内保留教师工作台能力；审批中心对教师显示本人办理事项 |
| 业务办理 | 培训项目管理、培训课程管理、培训基地管理、培训师资库、培训数据、培训成果 | 保留已确认的“业务办理”业务称谓；师资库与教师资质不混同 |
| 教师与资质 | 授课与学分、教师资质管理、授课认定 | 授课认定按专项授权显示 |
| 积分与考核 | 教师积分激励、三级考核管理、数据核对与复核 | 公示、申报、核对等保留在相应业务及上下文入口 |
| 分级管理与统计 | 个人数据看板、教研室与二级学院管理、学院台账与口径检查、学校管理驾驶舱 | 按现有业务授权显示；不因此让教师访问组织统计 |
| 系统管理 | 账号与权限、表格导入导出、对接与同步、规则与配置、日志与运行 | 管理资格与具体功能权限同时校验 |
| 固定辅助入口 | 操作指引 | 保留侧栏底部位置 |

共同菜单保持相对顺序。不可见项目不占空白位置，空分组隐藏。单一可用导出页允许显示“导出下载”，不冒充具备导入权限。

教师首页主内容可称“教师工作台”，其余角色为工作总览；这是首页职责差异，不延伸到资质、项目等共同业务的任意改名。

| 培训成果 `outcomes` | 培训成果 | 保留授权查询与认定依据，不以成果展示自动记分 |
| 教师积分激励 `points` | 教师积分激励 | 默认积分明细，查询、确认及更正能力保持 |
| 积分申报／社会培训积分认定 `recognition` | 教师积分激励的申报与认定页签 | 统一页签名称，保留现有业务路由 |
| 三级考核管理 `assessment` | 三级考核管理 | 保留教师和组织考核对象 |
| 学院年度考核／学院考核公示 `annual` | 三级考核管理的学院社会培训年度考核页签 | 教师只能读取获准公示内容；管理职责不扩张 |
| 我提出的核对／数据核对与复核 `disputes` | 数据核对与复核 | 本人发起与授权复核共用入口，保留上下文跳转 |
| 本教研室管理／本学院与教研室管理／学院与教研室 `organization` | 教研室与二级学院管理 | 与账号、组织配置分离；身份范围放在说明中 |
| 教研室平均积分／学院台账与口径检查 `ledgers` | 学院台账与口径检查 | 教研室只进入已授权平均积分区域，不能加载学院台账明细 |
| 培训课程视频分钟资源 `resources` | 原业务的资源统计辅助页 | 不新增主菜单，不删除旧链接；保留原授权 |
| 学校管理驾驶舱 `cockpit` | 学校管理驾驶舱 | 保留专用展示与原表来源说明 |
| 账号与权限 `permissions` | 账号与权限 | 同时校验系统管理员资格和功能权限 |
| 表格导入 `imports`、导出任务 `exports` | 表格导入导出 | 页签按权限显示；业务页导出入口保留 |
| 规则 `rules`、制度 `policy`、字典 `settings` | 规则与配置 | 保留原页签、规则历史与技术详情折叠 |
| 审计 `audit`、运行 `operations` | 日志与运行 | 保留原权限与运行查看入口 |
| 对接总览 `sync`、认证 `sso`、中台 `hub`、省平台 `province` | 对接与同步 | 统一父菜单定位；子功能不能随改名丢失 |
| 对接指引 `guide`、实施工具 `implementation` | 对接与同步的辅助页面 | 技术工具按原授权并默认折叠 |
| 操作指引 `help` | 操作指引 | 更新旧菜单称谓和路径，不能保留失效教程 |

从首页、消息、搜索、收藏、旧地址、业务详情返回主页面时，都使用上述对应关系；不得出现业务页有内容但侧栏完全不选中的情况。

## 7. 身份切换与页面状态

**需求04 保留业务位置并重新授权**

| 场景 | 规定行为 |
| --- | --- |
| 切换至另一个身份且业务仍可访问 | 保留主业务及仍可访问的页签，重新加载身份和数据 |
| 主业务可访问、原页签不可访问 | 进入该业务对新身份可用的默认页签，并提示范围已变化 |
| 主业务不可访问 | 返回工作总览，提示原页面不在当前身份授权范围 |
| 存在未保存编辑 | 提示继续编辑或放弃修改后切换；不静默丢弃，不自动提交 |
| 切换请求进行中 | 禁止重复切换与旧身份业务提交，显示明确进度 |
| 切换被后端拒绝 | 保留原身份及当前位置，说明原因 |
| 身份已切换但重新加载失败 | 显示加载失败与重试，不展示可操作的旧身份数据 |
| 点击已经选中的身份 | 收起身份面板，不因待办数量跳转页面 |
| 当前身份不具备切换选项 | 显示“账号信息”，不显示误导性的“切换角色”入口 |

第一版继续采用现有完整重新加载机制，不改成复杂的局部身份切换。

跨身份只保留业务与合法页签；清除选中记录、详情、分页、组织与教师筛选、关键词、期间及其他查询条件。旧身份请求结果不得覆盖新身份页面。

同一身份下，从列表进入详情再返回，应恢复原列表筛选与分页；办理结果刷新后若记录不再符合条件，说明原因，不静默消失。

页面刷新及浏览器前进后退必须重新判断当前授权。来自旧地址的教师、组织、记录编号不能作为授权依据。

## 8. 共同业务页面要求

### 8.1 通用结构

共同页面采用：标题与查看范围、业务页签、必要汇总、筛选区、记录列表、详情与办理。

- 同一业务的公共字段名称和相对顺序一致；管理角色可以增加教师、组织等必要字段。
- 同一指标有不同范围时写明期间、来源、单位与认定状态，不以模糊的“总数”代替。
- 无权限操作隐藏；有权限但当前状态不允许的必要操作说明不可用原因。
- 读取失败、无记录、无匹配结果、无权限、等待学校配置分别呈现。
- 页面说明和长流程引导默认折叠；当前阻断原因和必须处理的事项不能折叠隐藏。
- 未加载成功不能显示为零；明确的零收入、零积分等真实值不能显示为未提供。
- 表格操作列应易于到达。常驻摘要不得挤压到主要字段和办理按钮难以使用。
- 列表选中摘要使用“查看摘要”，打开完整业务使用“查看详情”，不让同一文案产生两种不同结果。
- 保留键盘可操作、当前菜单及页签状态标识、输入标签、弹窗焦点与返回焦点。

### 8.2 项目

**需求05 项目主入口统一**

- 复用现有项目业务查询及完整详情，默认进入业务办理。
- 教师默认查看本人申报；提供本人负责或参与范围。两种范围名称明确，不将两个数量解释为同一总数。
- 教研室、学院、学校默认查看授权业务范围，不自动以历史资料取代。
- 历史资料作为页内辅助入口，保留原表、来源、待核信息和关联材料，不修改原历史记录。
- 项目草稿、申报、备案、实施、结项仍是同一项目的生命周期，不通过页面合并复制对象。
- 申报按钮调用现有表单。草稿、退回、审批中、已备案和已结项均有明确定位。
- 首屏优先显示项目名称、负责人或本人关系、状态和操作；封面与摘要不能占据主要办理空间。

### 8.3 教师资质

**需求06 共用证书列表和详情**

- 复用教师端证书展示、状态分类和有效期表达；管理范围增加教师、组织及必要版本信息。
- 有效、即将到期、已过期等统计必须由授权查询计算，不能把单页数量当成范围总数。
- 图片预览按附件权限展示，不因管理角色能看文字就默认放开所有附件。
- 复用现有证书详情、审核记录、历史版本、附件预览和下载。
- 本人编辑、提交、补正与管理审核仍按原权限和记录状态区分。

### 8.4 课程、基地、师资、培训数据与成果

**需求07 共用业务入口并保留记录类型**

| 业务 | 统一内容 | 必须保留 |
| --- | --- | --- |
| 培训课程 | 申报记录与课程库在同一业务下，公共字段及详情入口一致 | 教务／超星来源、手动填写、资源、申报记录与入库课程的关联 |
| 培训基地 | 本人申请与授权基地清单清楚分区 | 校内外属性、用途、认定依据、生效日期与原申请 |
| 培训师资 | 资格申请、认定状态与师资记录清楚分区 | 一人一单、校内遴选、外聘备案、专项认定职责 |
| 培训数据 | 以明细列表为主，详情按需打开 | 教师授课业务与教师本人参训分开，来源和更正依据保留 |
| 培训成果 | 统一列表、状态、来源与详情 | 登记展示不等同计分，贡献归属与认定依据不删除 |

申报与正式业务记录不是两份可以相加的业务量。申报通过后，应能从正式记录回溯申请及材料。

教师进入师资统一入口，仅获得原本允许的本人申请和本人资格内容，不因此开放师资库查询。其他共享资源是否可见，沿用已有被确认的服务端授权，不在本次设计中推定。

### 8.5 积分

**需求08 统一明细和认定入口**

- 主菜单保留“教师积分激励”，统一页签采用“积分明细”“申报与认定”，不按角色改名。
- 默认进入积分明细，汇总、筛选、流水顺序一致。教师本人确认作为独立职责区域保留。
- 教师流程引导收进页面说明，避免每次查看积分先经过大段入门内容。
- 申报与认定复用已有清单、完整流程、退回、更正、汇总公示及历年折算。
- 历年折算、授课积分和辅助积分分别表达，不混同原始分值、调整分值和累计分值。
- 本人确认作用于完整周期台账时，必须持续说明筛选不缩小确认范围。
- 已归档结果、规则版本、追加更正和原始依据保持可追溯；本次不改变算法。

### 8.6 考核

**需求09 共用查询与详情，明确对象**

- 主菜单保留“三级考核管理”。
- 第一层区分现有“三级考核”和“学院社会培训年度考核”；前者内部按授权选择教师、教研室、学院、学校对象。
- 教师默认本人教师考核，保留最近周期结果摘要和过程状态；结果列表与管理端使用一致的字段语义。
- 对象选择、期间筛选、处理进度筛选分别承担不同作用，不再用多排外观相同的页签混淆。
- “学院考核”与“学院社会培训年度考核”分别说明制度依据；未确认同一对象与同一规则前不合并数据。
- 教师进入年度考核区域时仅显示获准公示记录，并标明“公示内容”，不暴露管理材料或审批动作。
- 完整流程、退回原因、确认状态和归档记录复用现有详情。
- 排名注明当前范围与周期；多周期列表不被表述为某一年度全校排名。

### 8.7 通知、组织业务与系统管理

**需求10 功能归属清楚**

- 政策通知使用同一列表结构与阅读详情；学校按权限增加发布、编辑和撤回。
- 教研室与二级学院管理保留业务概况、待办、进度和教师名册；不要与“账号与权限”中的组织配置混为一个功能。
- 组织业务名称采用采购文件对应名称，当前范围通过副标题表达，不再用多套菜单名称替代同一入口。
- 系统管理保留现有组合页，单一功能的标题与父菜单有明确归属。
- 规则、对接和运行的技术细节默认折叠，标注“实施人员使用”。

**需求11 组织名称与查看范围正确**

- 已获准查看的记录，应显示相应业务组织的可读名称。
- 不通过扩大组织名册或数据权限解决名称缺失；优先使用授权记录携带的展示名称或受限关联查询。
- 确实无权或资料缺失时，分别写“当前身份不可见”“资料待补充”，不能统一用“—”掩盖原因。
- 公示、共享资源、专项授课认定的范围不能笼统标成“仅本人”。

## 9. 统计与提醒口径

**需求12 首页与明细同源同口径**

| 场景 | 规定 |
| --- | --- |
| 学校原始资料汇总 | 使用与学校原件采用版本一致的来源集合，测试及其他来源不混入 |
| 人次与人天同时存在 | 分开显示数值和单位，不生成跨单位总人次 |
| 未核定值 | 标注报送值、推荐试算或待核定，不伪装为正式认定数 |
| 期间不同 | 明确全年、阶段资料或当前业务期间，不能默认同比 |
| 首页进入详情 | 传递对应来源、期间和单位范围，保证能解释汇总数 |
| 导出 | 与当前明确选定的业务范围、来源和单位一致；保留必要口径说明 |
| 个人数据与学院数据 | 归属收入、项目到账收入、课程人次和学院报送量分别命名，不强行相等 |

统计修正先复用驾驶舱与台账已有的原件匹配及单位划分能力，修正首页引用；禁止另写一套脱离来源的总数。是否影响既有导出必须逐条核验。

本批只修正展示及汇总范围，不修改原始台账、核定值、积分或已归档考核。发现历史计算也受影响时另列缺陷，不自动重算。

**需求13 提醒与审批计数对应**

- 右上角“待办与通知”入口说明总数包含哪些事项。
- 业务审批、同步异常、安全提示、资质到期等分别可定位；同一计数与所进入清单使用一致过滤条件。
- 审批中心可以只显示业务办理，但标题和计数必须说明其范围；其他提醒不能从总数中消失后无处可找。
- 不能简单把各业务模块数量相加后当作去重总数，同一事项多入口只计一次。
- 待读取、读取失败及暂不可用不显示为零；提供重试，旧值需标明尚未刷新。

## 10. 接口、数据与兼容要求

**需求14 复用现有能力并保护业务**

1. 优先复用现有身份、本人申请、业务查询、详情和办理接口，不新增宽权限聚合接口。
2. 本人申请与业务库采用各自原有授权；不能把原本只需本人门户权限的申请入口改成必须拥有管理查询权限。
3. 页面映射和旧链接兼容不改变业务对象编号，不复制项目、申请或积分记录。
4. 不计划新增数据库结构或数据迁移。若实施发现确有必要，先作为范围变化说明，不能隐式加入。
5. 统计接口如需调整，应同步核对全部调用方、导出和回归检查；保留明确的来源、单位、期间与认定状态表达。
6. 切换身份后附件、下载、导出任务和旧详情都重新校验当前权限，不能沿用旧身份结果。
7. 同一业务有多处入口时复用原办理函数，避免复制审批逻辑。
8. 空值与显式零保持区别；所有金额、人次、积分继续使用现有业务精度。
9. 搜索与分页应明确范围。已有仅对当前页生效的筛选不得标成全量筛选；大样本场景须验证，不凭小样本宣布通过。

## 15. 完成定义

本次改造完成必须同时满足：

1. 最终菜单映射无遗漏，学校文件对应功能仍可定位，旧入口与历史资料保留。
2. 共同业务在四角色下可识别为同一功能，公共导航与操作方式稳定。
3. 切换身份不丢失合法业务位置，也不残留旧身份数据与权限。
4. 资质、申请、积分、考核的记录、附件、流程和历史未被页面整合破坏。
5. 指标及提醒的数量有明确口径，汇总可穿透，分单位结果与导出一致。
6. 第11节适用验收项通过；未适用项说明原因，未完成项不标通过。
7. 交付报告明确区分代码检查、本地业务验证、真实学校集成和生产验收。

本需求文档不声称所有边界都已实测。尚待补齐的真实兼任身份、完整表单状态、附件与导出、大样本分页及正式学校验收，已纳入验收和待确认清单，不应在施工中被遗漏。
