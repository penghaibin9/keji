## 1. 本轮实际修复

| 项目 | 原问题 | R9修复与证据 |
|---|---|---|
| 成功回执保护 | 同一业务重复提交时会拿到原任务；接口此时掉线，路由又把原DONE任务及成功明细改为BLOCKED。 | 入队明确返回是否新建；只有新任务才登记初始阻断。重复业务请求不重写原任务、明细及成功回执。 |
| 尝试编号 | 未连通重复提交不断追加attempt=1，而task.attempts仍为0。 | 只登记一次初始阻断，并同步增加任务尝试次数；重复请求只返回旧结果。 |
| 补传状态陈旧 | 明细在锁之前已经加载；等待父任务后仍拿旧对象判断失败，可能把已完成明细重新排队。 | 父任务按顺序加锁后重新加载明细并populate_existing，成功行不补传；相应测试控制ORM陈旧对象，不宣称真实MySQL并发。 |
| 锁后版本复核 | 单条或批量补传在等锁之前验证版本，可能忽略等待期间的版本变化。 | 服务层在锁后重复核对调用方期望的任务/明细版本；冲突409而不重排。 |
| 发送前整批一致性 | 缺失/复用明细或被改变的报文、摘要、幂等键、类型、连接，可能在发送部分正常行之后才被发现。 | 第一次外部调用之前检查整个批次的数量、关联、所有权、数据类型、内容摘要与幂等键；不一致整批BLOCKED且0适配器send。 |
| 终态保护 | 直接再次调用同步/拉取执行器，会让DONE、FAILED、BLOCKED任务继续执行。 | 只有PENDING/RETRY可进入执行器；其他终态原样返回，必须经过显式授权重试流程。 |
| 连接证明先后顺序 | 同一秒内的多次验证按时间+随机UUID排序，可能激活旧成功而忽略新失败，或拒绝最新成功。 | 验证和启用都取得连接锁；新证明绑定递增连接版本，启用与运行只接纳相应版本的唯一证明。相同时间、倒退时钟、重复证明均控制验证。 |
| 最近接口记录 | 驾驶舱只取全系统最近500个任务再找接口，较早接口会显示尚无任务。 | 按连接直接查询最近任务，并支持connection_id/data_type筛选；501条无关记录不会遮掉目标接口。 |
| 传输/业务完成分离 | 拉取生成预览也显示成功1条；真正入库多条却仍显示成功1。 | 摘要读取正式批次与逐笔记录，显示成功/失败/待确认条数；手动确认后读取最新正式回执；0行拉取显示无新增，不能把失败0条当作任务成功。 |
| 严格配置与长度 | 配置中的3.8次重试或1.5分钟被int截断；超长业务键SQLite能存而MySQL列容量不接受。 | 拒绝小数截断、布尔值及非法数值；精确整数文本保留兼容；业务唯一键超过160字符时入队前422。 |
| 组装完整性 | 新运行状态模块必须包含在完整源码包中。 | `check_assembly.py`加入integration_status.py必需文件检查，避免漏包仍绿灯。 |

主要改动：`backend/app/integrations.py`、`sync_policy.py`、`inbound_sync.py`、`integration_status.py`、`routes/integrations.py`及前端驾驶舱的状态/计数展示。未改积分/考核计算口径、未重写主数据模块、未新建另一套系统。

报文摘要只能发现不完整或不一致内容，不是防数据库管理员整体改写的数字签名。发送前检查不能撤回已经发出的外部请求；远端幂等行为、超时后的确认和实际并发竞争必须用学校协议及真实环境验证。

状态汇总的成功/失败/待确认是记录数。无逐行数据的传输失败可以为0条失败，但任务状态仍FAILED/BLOCKED，不能据此推断同步成功。历史拉取任务的transport receipt不因人工确认而被改写；摘要单独回读正式批次。
